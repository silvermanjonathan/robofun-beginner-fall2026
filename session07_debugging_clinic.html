Opener · 10 minutes

Retrieval: name that error

Five short broken lines are on the board. Write the error name next to each. No editor until all five are written.

Question: pritn("hi")

NameError. Python does not know that word.

Question: print("3" + 1)

TypeError. Text and number cannot be added.

Question: riders = ["a", "b"] then print(riders[2])

IndexError. Two slots, numbered 0 and 1.

Question: for i in range(3) with no colon at the end

SyntaxError. Punctuation. Python stops before running anything.

Question: for i in range(3): then print(i) on the next line with no indent

IndentationError. The block after the colon is missing.

Chunk 1 of 6

The last line names the category

A traceback reads bottom to top. The last line gives you the error name and usually the exact word involved. Read that first, every time, before you look at anything else.

riders = ["Ada", "Grace", "Alan"]
total = 0
for r in riders:
    total = total + r
print(total)

Predict: This loop adds names to a number. Which of the five error names do you expect?

What it actually prints

Traceback (most recent call last):
  File "Jonathan_session07.py", line 4, in <module>
    total = total + r
            ~~~~~~^~~
TypeError: unsupported operand type(s) for +: 'int' and 'str'

TypeError, and the message names both kinds involved. The bug is not the loop. It is that total holds a number and r holds text.

Chunk 2 of 6

The line number is where Python noticed

Python names the line where it gave up, which is not always the line you got wrong. Here the accumulator is misspelled on line 1 and the program runs fine until line 3 asks for a name that was never created.

totl = 0
for n in [52, 47, 61]:
    total = total + n
print(total)

Predict: The typo is on line 1. Which line number does Python name?

What it actually prints

Traceback (most recent call last):
  File "Jonathan_session07.py", line 3, in <module>
    total = total + n
            ^^^^^
NameError: name 'total' is not defined. Did you mean: 'totl'?

Line 3, where the missing name got used. The mistake is two lines above that. Read the suggestion at the end as well: Python offers totl, which is the typo itself, and that is the fastest pointer to the real line. When the named line looks correct, the bug is usually above it.

Chunk 3 of 6

Indentation is a real error, with its own name

Python uses indentation to decide what belongs to what. An extra space or a missing one is not a style issue here; it changes the program or stops it.

for i in range(3):
print(i)

Predict: The print is not indented. Does Python guess what you meant?

What it actually prints

  File "Jonathan_session07.py", line 2
    print(i)
    ^
IndentationError: expected an indented block after 'for' statement on line 1

No. It names the error and asks for the indented block. Python never guesses. This is a feature, though it takes a term to believe it.

Chunk 4 of 6

Loud bug against silent bug

A loud bug stops the program and tells you where. A silent bug runs to the end and hands you the wrong answer with no complaint at all. Silent bugs cost more, so learning to doubt a plausible answer is part of the job.

heights = [52, 47, 61]
for h in heights:
    total = 0
    total = total + h
print("total:", total)

Predict: No error appears. Is 160 what prints?

What it actually prints

total: 61

No, it prints 61. The reset sits inside the loop, so each pass throws away the last one. The answer looks like a total and is really just the last height. This exact bug was the hinge question in session 3.

Chunk 5 of 6

The print probe

When a program runs but lies to you, put a print inside the loop and watch the values move. Label it so you can find it and delete it later.

heights = [52, 47, 61]
total = 0
for h in heights:
    total = total + h
    print("probe: h =", h, "total =", total)
print("final:", total)

Predict: Three passes. How many probe lines appear, and what is the total after the second one?

What it actually prints

probe: h = 52 total = 52
probe: h = 47 total = 99
probe: h = 61 total = 160
final: 160

Three probes, and 99 after the second. Once you can see the values change, the bug stops being a mystery and becomes a reading task.

Chunk 6 of 6

One change per run

Change one thing. Run it. Write down what happened. Change the next thing. Two changes at once means that when the program improves, you do not know which change did it, and when it breaks you do not know which one to undo.

def fare(age):
    if age < 5:
        return 0
    if age < 13:
        return 8
    return 12

print(fare(4), fare(5), fare(12), fare(13))

Predict: Which of the four calls sit on a boundary, and do they all return the value you want?

What it actually prints

0 8 8 12

All four are boundary tests: 4 and 5 straddle the first gate, 12 and 13 the second. 0, 8, 8, 12. Testing the boundaries is how you find gate bugs, and it takes one line.

Hinge question · reaches back to session 4

Before you build

Question: From session 4: a function is supposed to return the sum of a list and always returns the first number instead. No error appears. Where is the bug, and which of the two bug types is it?

return is indented inside the loop, so the function quits on the first pass. Silent bug. It hands back a number that looks reasonable, which is exactly what makes it expensive.

Build · 25 minutes

Build: five broken cards

  1. For each card: write the error name before you run it.
  2. Run it. Read the last line first.
  3. Write the fix in one line, then apply it.
  4. Run again. One change per run.
  5. Card 5 has no error message at all. Find it with a probe.

Card 1

riders = ["Ada", "Grace"]
print("Riders on board: " + len(riders))

Predict: Text plus a number. Which error name, and on which line?

What it actually prints

Traceback (most recent call last):
  File "Jonathan_session07.py", line 2, in <module>
    print("Riders on board: " + len(riders))
          ~~~~~~~~~~~~~~~~~~~~^~~~~~~~~~~~~
TypeError: can only concatenate str (not "int") to str

TypeError on line 2. len hands back a number and a plus sign cannot glue it to text. One fix: put both inside an f-string.

Card 2

for h in [52, 47, 61]
    print(h)

Predict: Nothing is misspelled. What is missing, and does Python run any of it?

What it actually prints

  File "Jonathan_session07.py", line 1
    for h in [52, 47, 61]
                         ^
SyntaxError: expected ':'

The colon. SyntaxError, and Python stops before running a single line. One change fixes it.

Card 3

player = "Ada"
scroe = 15
bonus = 5
print(f"{player} has {score + bonus} points")

Predict: The typo is on line 2. Which line does Python name?

What it actually prints

Traceback (most recent call last):
  File "Jonathan_session07.py", line 4, in <module>
    print(f"{player} has {score + bonus} points")
                          ^^^^^
NameError: name 'score' is not defined. Did you mean: 'scroe'?

Line 4, where the missing name is used. NameError, and Python suggests scroe, which points at the real line. Fix line 2, not line 4.

Card 4

riders = ["Ada", "Grace", "Alan"]
for i in range(4):
    print(i, riders[i])

Predict: Three riders, four passes. How many names print before the error?

What it actually prints

0 Ada
1 Grace
2 Alan
Traceback (most recent call last):
  File "Jonathan_session07.py", line 3, in <module>
    print(i, riders[i])
             ~~~~~~^^^
IndexError: list index out of range

Three, then IndexError on the fourth pass. Change the 4 and nothing else. range(len(riders)) is the version that survives adding a rider.

Card 5

heights = [52, 48, 61, 44, 58]
cleared = 0
for h in heights:
    if h >= 48:
        cleared = cleared + 1
print("riders over 48 inches:", cleared)

Predict: No error. The rule is over 48 inches. Is the printed count right?

What it actually prints

riders over 48 inches: 4

No. It prints 4 and the right answer is 3, because 48 is not over 48. A probe inside the loop shows the 48 being counted. This is a boundary bug from session 2, and it is silent.
