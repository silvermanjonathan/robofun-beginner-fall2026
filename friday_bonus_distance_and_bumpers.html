Question: Why does a bounce test have to include the radius?

Because the position is the centre. Without the radius the circle is already half inside the wall when the test fires.

Chunk 1 of 5

The straight-line distance between two points

Take the difference across, take the difference down, square both, add them, and take the square root. That is the Pythagorean theorem with the right triangle left implicit: the two differences are the legs and the distance is the hypotenuse.

import math

ax = 100
ay = 100
bx = 130
by = 140

dx = bx - ax
dy = by - ay
print("dx =", dx, " dy =", dy)
print("distance =", math.sqrt(dx * dx + dy * dy))

Predict: The differences are 30 and 40. What is the distance?

50, exactly. The three-four-five triangle, scaled by ten. Squaring removes the sign, which is why the order you subtract in does not matter.

What actually happens

dx = 30  dy = 40
distance = 50.0

Chunk 2 of 5

A distance function

Four parameters in, one number out. This is the most reused function in any game you will write.

import math

def distance(ax, ay, bx, by):
    dx = bx - ax
    dy = by - ay
    return math.sqrt(dx * dx + dy * dy)

print(distance(0, 0, 3, 4))
print(distance(3, 4, 0, 0))
print(distance(100, 100, 100, 150))
print(round(distance(0, 0, 1, 1), 4))

Predict: The first two calls swap the points. Do they give the same answer?

Yes. Squaring makes the direction irrelevant. The last one is the square root of two, which is the first answer today that is not a whole number.

What actually happens

5.0
5.0
50.0
1.4142

Chunk 3 of 5

Two circles overlap when the distance is small enough

Two circles touch when the distance between their centres equals the sum of their radiuses. Less than that and they overlap. One comparison, no rectangles, and it works at any angle.

import math

def distance(ax, ay, bx, by):
    dx = bx - ax
    dy = by - ay
    return math.sqrt(dx * dx + dy * dy)

BALL_R = 20
BUMPER_R = 30

def hits(bx, by, px, py):
    return distance(bx, by, px, py) < BALL_R + BUMPER_R

print(hits(100, 100, 120, 115))
print(hits(100, 100, 200, 200))
print(hits(100, 100, 130, 140))

Predict: The radiuses add to 50. The third call has centres exactly 50 apart. Does that count as a hit?

No. The first is a hit at 25 apart and the second is a clear miss, but the third comes back False because the test is strictly less than. Exactly touching is not overlapping. Whether you want that boundary counted as a hit is a design decision, and it is the kind that turns up later as one very confusing bug.

Chunk 4 of 5

Skipping the square root

Square roots are slower than multiplication, and here you do not need one. If you compare the squared distance to the squared sum of radiuses, the comparison gives the same answer with less work. Squaring both sides of a comparison between positive numbers does not change which side is larger.

def hits_fast(bx, by, px, py, r_sum):
    dx = px - bx
    dy = py - by
    return dx * dx + dy * dy < r_sum * r_sum

print(hits_fast(100, 100, 120, 115, 50))
print(hits_fast(100, 100, 200, 200, 50))
print(hits_fast(100, 100, 130, 140, 50))
print(50 * 50, "against", 30 * 30 + 40 * 40)

Predict: Compare these three answers to the three from the last chunk. Any differences?

None. Same three answers, no square root anywhere. The last line shows why the boundary case still lands in the same place: 2500 against 2500. Squaring both sides of a comparison between two positive numbers does not change which side is larger, so the square root was never doing any work. This trick is everywhere in game code, and now you know it is not a trick.

Chunk 5 of 5

A bumper that bounces and scores

Put it together. When the ball hits the bumper, reverse both velocities and add to the score. The probe prints the frame of each hit so you can check the count rather than trusting your eyes.

import math
import pygame

pygame.init()
WIDTH = 640
HEIGHT = 480
BALL_R = 20
BUMPER_R = 30
screen = pygame.display.set_mode((WIDTH, HEIGHT))
clock = pygame.time.Clock()

def distance(ax, ay, bx, by):
    dx = bx - ax
    dy = by - ay
    return math.sqrt(dx * dx + dy * dy)

x = 100
y = 100
vx = 6
vy = 5
bump_x = 320
bump_y = 240
score = 0
frame = 0
was_touching = 0

running = 1
while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = 0
    x = x + vx
    y = y + vy
    if x < BALL_R:
        vx = -vx
    if x > WIDTH - BALL_R:
        vx = -vx
    if y < BALL_R:
        vy = -vy
    if y > HEIGHT - BALL_R:
        vy = -vy

    touching = 0
    if distance(x, y, bump_x, bump_y) < BALL_R + BUMPER_R:
        touching = 1
    if touching == 1 and was_touching == 0:
        vx = -vx
        vy = -vy
        score = score + 100
        print("hit on frame", frame, "score", score)
    was_touching = touching

    frame = frame + 1
    screen.fill((27, 41, 81))
    pygame.draw.circle(screen, (220, 38, 38), (bump_x, bump_y), BUMPER_R)
    pygame.draw.circle(screen, (252, 211, 77), (int(x), int(y)), BALL_R)
    pygame.display.flip()
    clock.tick(60)

print("final score", score, "after", frame, "frames")
pygame.quit()

Predict: Take out was_touching and the gate that uses it. What happens to the score on a single hit?

It climbs every frame the ball is inside the bumper, which is several hundred points for one hit. The was_touching name is there so the score changes on the frame the contact begins and not again until contact ends. This is the same problem as a coin collected once per frame in session 11.

What actually happens (run without a screen, quit after 240 frames)

hit on frame 28 score 100
hit on frame 115 score 200
hit on frame 202 score 300
final score 300 after 241 frames

Hinge question · reaches back two weeks

Before you build

Question: From session 10: why does flipping both velocities look wrong when the ball hits the bumper straight on from the side?

Because a real bounce only reverses the direction that ran into the surface. Flipping both sends the ball back along its exact incoming path, which looks like the bumper grabbed it. Doing it properly means working out the direction from the centre outward, which is a good reason to leave this as a bonus.

Running this in VS Code

Once, before the first run

Open the terminal in VS Code and install the library: pip install pygame. Check it worked with python -c "import pygame", which should print nothing at all. An error here is an install problem, not a problem with your program.

Every run after that

The window often opens behind VS Code, so check the taskbar before deciding nothing happened. Close it with its own close button: these programs are written to end when the window closes, and stopping the terminal instead can leave the window stuck on screen. A window that will not close usually means the loop has no pygame.event.get() in it.

There is no turtle anywhere in this course. Turtle needs a library our VS Code setup does not have, so pygame does all the drawing, starting in session 5.
