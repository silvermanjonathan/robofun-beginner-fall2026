Opener · 10 minutes

Retrieval: the ledger card, out loud

Cards on the desk. Find the stamp for the thing you are about to change in your engine, and read it to the person next to you. If you cannot find it, that is the first thing to fix today.

Question: Which stamp covers the numbers at the top of your engine?

Stamp 10, the knob block. Every number you are about to change lives there.

Question: Which stamp tells you what to do when your change makes the program worse?

Stamp 7. One change per run, and undo the last one before trying the next.

Chunk 1 of 4

The commission: two required changes

You are handed a working engine. You do not rewrite it. You change its behaviour through the knob block and through one named function, and you keep it working the whole time. This is what most programming work actually looks like.

# CHANGE 1: through the knob block only.
#   Make the game harder without touching any line below the block.
#   Acceptable: speed, spawn interval, lives, tile size, colours.

# CHANGE 2: through one function only.
#   Add a rule the engine does not have yet. One function, one gate.
#   Examples: a tile that costs a life, a coin worth five,
#   a wall that opens once the score passes ten.

Predict: Change 1 forbids editing anything below the knob block. What does that tell you about how the engine was written?

That every number the behaviour depends on was given a name at the top. If you find a raw number buried in the loop that you need to change, that is a fault in the engine, and naming it is a legitimate third change.

Chunk 2 of 4

The expected and got sheet

Before you run a change, write what you expect. After you run it, write what you got. When the two columns differ, you have found something, and you have it in writing. This is the artifact, not the code.

# CHANGE: SPAWN_EVERY from 90 to 45
# EXPECTED: coins appear twice as often, roughly every 0.75 seconds
# GOT:      ?
#
# CHANGE: lives from 3 to 1
# EXPECTED: game over on the first hit
# GOT:      ?

Predict: Why write the expectation before running rather than after?

Because afterwards you will believe you expected whatever happened. Writing it first is the only way to catch the times you were wrong, which are the times you learn something.

Chunk 3 of 4

The sixty-second demo: run, point, tell

Three beats, twenty seconds each. Run the program. Point at the thing you changed. Tell us what it does and why you chose it. You are not explaining all of Python. You are explaining one decision.

RUN   (20s): start it, let it play, say what the game is in one sentence.
POINT (20s): show the line or the number you changed. Read it out.
TELL  (20s): say what it does now that it did not do before,
             and name one thing that broke on the way there.

Predict: Which of the three beats is hardest to do in twenty seconds?

Tell. Most people describe what the code says instead of what it does. Rehearse the sentence out loud twice before the room fills up. Naming the thing that broke is not a confession, it is the interesting part.

Chunk 4 of 4

One honest name

One exit criterion today is naming. If a function is called check and it removes a life, rename it. The summer example in this program is the function once called create_fox that made any animal; it is create_animal now.

# Before
def check(row, col):
    return level[row][col] == 0

# After
def is_open(row, col):
    return level[row][col] == 0

Predict: Both versions run identically. Why is the rename worth a minute on demo day?

Because the person reading it next is you, in three months, with no memory of what check checked. A name is the shortest comment you can write, and it cannot fall out of date the way a comment can.

Hinge question · reaches back two weeks

Before you build

Question: Pick any stamp on your ledger card from before session 7 and state the bug it was written to prevent.

Accept any correct pairing. The common strong answers: stamp 1 and the int() trap, stamp 3 and the accumulator reset inside the loop, stamp 4 and a function that prints instead of returning, stamp 6 and a strip whose result was never stored.

Build · 45 minutes

The commission

  1. Make change 1 through the knob block. Fill in the expected and got sheet before and after.
  2. Make change 2 through one function. Fill in the sheet again.
  3. Make one change of your own choosing, and write it on the sheet the same way.
  4. Rename one thing in the program so the name matches what it does.
  5. Rehearse run, point, tell twice. Time yourself.

Expected and got

Fill in the left column before you run. Fill in the right column after.

Where you can stop

All three are real landings. Nobody is behind for finishing at the floor.

Floor

One knob change, working, and a sixty-second demo that runs the program and points at the change.

Middle

Both required changes plus one of the student's own, with a completed sheet and a rehearsed demo.

Stretch

Write four lines at the top of the file explaining what the program does and what you changed, in the shape of the README entry it would need if you published it.

Ledger card

Stamp 12: signed off. Write one sentence on the back of the card naming the single hardest bug you fixed this term and how you found it.

Timing, 90 minutes
