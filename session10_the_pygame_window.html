Chunk 1 of 6

The window has its own coordinates

A callback to session 5, where a heading of 90 degrees pointed at the floor. The top left corner is 0, 0. The first number moves right and the second moves down, which is upside down from the graph paper you use in maths class. Everything else about ordered pairs is the same.

import pygame

pygame.init()
WIDTH = 640
HEIGHT = 480
screen = pygame.display.set_mode((WIDTH, HEIGHT))

print("top left    ", (0, 0))
print("top right   ", (WIDTH, 0))
print("bottom left ", (0, HEIGHT))
print("centre      ", (WIDTH / 2, HEIGHT / 2))
pygame.quit()

Predict: Which corner holds the pair 0, 480?

What it actually prints (run without a screen)

top left     (0, 0)
top right    (640, 0)
bottom left  (0, 480)
centre       (320.0, 240.0)

The bottom left. Larger second numbers are lower on the screen. Write this on the ledger card, because every position bug for the rest of term starts here.

Chunk 2 of 6

The frame loop, taken apart

You have run this before. In session 5 it sat under your drawing and you were told to copy it. Here is what each line does. The loop runs until running becomes 0, nothing else ends it, and the window never closes itself. clock.tick(60) holds the speed steady at sixty passes a second. The difference from session 5 is that the drawing now happens inside the loop, which is what lets it change.

import pygame

pygame.init()
screen = pygame.display.set_mode((640, 480))
clock = pygame.time.Clock()

running = 1
while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = 0
    screen.fill((27, 41, 81))
    pygame.draw.circle(screen, (252, 211, 77), (320, 240), 30)
    pygame.display.flip()
    clock.tick(60)

pygame.quit()

Predict: Name the one thing that can make this loop stop.

Nothing printed in the terminal. This was run without a screen and quit after 5 frames, and it printed nothing because the window is the output. Words go in the terminal, visuals go in the window.

Clicking the window's close button, which puts a QUIT event in the queue and sets running to 0. That is the exit condition, written in the loop, the way every while loop has had one since session 2. Compare this to session 5: there the fill and the drawing sat above the loop and ran once, and here they sit inside it and run sixty times a second.

Chunk 3 of 6

Draw order: last one wins

Drawing paints over whatever is already there. The fill goes first because it wipes the previous frame. Whatever you draw last sits on top.

import pygame

pygame.init()
screen = pygame.display.set_mode((640, 480))
clock = pygame.time.Clock()

running = 1
while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = 0
    screen.fill((27, 41, 81))
    pygame.draw.rect(screen, (248, 250, 252), (260, 180, 120, 120))
    pygame.draw.circle(screen, (220, 38, 38), (320, 240), 40)
    pygame.display.flip()
    clock.tick(60)

pygame.quit()

Predict: Swap the rect and circle lines. What changes on screen?

Nothing printed in the terminal. This was run without a screen and quit after 5 frames, and it printed nothing because the window is the output. Words go in the terminal, visuals go in the window.

The square covers the circle instead. Move the fill line below them and the screen goes blank, because the wipe happens last and erases your work. One change per run.

Chunk 4 of 6

Velocity is two numbers you add every frame

Position is where the ball is. Velocity is how far it moves in one frame. Adding the velocity to the position once per pass is the whole of animation. The probe prints the first few frames so you can watch the numbers rather than the pixels.

import pygame

pygame.init()
screen = pygame.display.set_mode((640, 480))
clock = pygame.time.Clock()

x = 320
y = 240
vx = 4
vy = 3
frame = 0

running = 1
while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = 0
    x = x + vx
    y = y + vy
    frame = frame + 1
    if frame < 6:
        print("frame", frame, "at", x, y)
    screen.fill((27, 41, 81))
    pygame.draw.circle(screen, (252, 211, 77), (x, y), 20)
    pygame.display.flip()
    clock.tick(60)

pygame.quit()

Predict: vx is 4 and vy is 3. After five frames, how far has the ball moved in each direction?

What it actually prints (run without a screen, quit after 8 frames)

frame 1 at 324 243
frame 2 at 328 246
frame 3 at 332 249
frame 4 at 336 252
frame 5 at 340 255

Twenty across and fifteen down. The position is the dependent quantity and the frame number is the independent one, which is the relationship you graphed in maths as a table of ordered pairs.

Chunk 5 of 6

A bounce is a sign flip, behind a flat gate

When the ball reaches an edge, reverse that direction by negating it. Two separate gates, one per edge, never nested. The radius has to be part of the test or the ball sinks halfway into the wall before it turns.

import pygame

pygame.init()
WIDTH = 640
HEIGHT = 480
R = 20
screen = pygame.display.set_mode((WIDTH, HEIGHT))
clock = pygame.time.Clock()

x = 600
y = 240
vx = 12
vy = 0
frame = 0

running = 1
while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = 0
    x = x + vx
    y = y + vy
    if x < R:
        vx = -vx
    if x > WIDTH - R:
        vx = -vx
    if y < R:
        vy = -vy
    if y > HEIGHT - R:
        vy = -vy
    frame = frame + 1
    if frame < 7:
        print("frame", frame, "x =", x, "vx =", vx)
    screen.fill((27, 41, 81))
    pygame.draw.circle(screen, (252, 211, 77), (x, y), R)
    pygame.display.flip()
    clock.tick(60)

pygame.quit()

Predict: The ball starts at 600 moving right at 12. On which frame does vx turn negative?

What it actually prints (run without a screen, quit after 9 frames)

frame 1 x = 612 vx = 12
frame 2 x = 624 vx = -12
frame 3 x = 612 vx = -12
frame 4 x = 600 vx = -12
frame 5 x = 588 vx = -12
frame 6 x = 576 vx = -12

On frame 2, when x lands on 624. The test fires after the move, so the ball is drawn once at 624, which is four pixels past the 620 limit, and only then turns around. That single frame of overshoot is why a ball appears to touch the wall rather than stop short of it, and it is also why a speed larger than the ball is a real problem.

Chunk 6 of 6

The knob block

Every number you might want to change goes at the top with a capitalised name. Nothing below the block has a raw number in it. This is what makes the commission in session 12 possible: you will be handed an engine and asked to change its behaviour without reading all of it.

WIDTH = 640
HEIGHT = 480
R = 20
SPEED_X = 12
SPEED_Y = 7
BG = (27, 41, 81)
BALL = (252, 211, 77)
FPS = 60

Predict: Nothing runs here. Why put the block at the top rather than next to the code that uses each number?

So that changing the behaviour takes one visit to one place. A number buried in the middle of a loop is a number nobody will find in session 12, including you.

Hinge question · reaches back two weeks

Before you build

Question: From session 4: rewrite the four bounce gates as a function bounce(pos, vel, low, high) that returns the new velocity. Then say why the function has to return rather than print.

def bounce(pos, vel, low, high): with two flat gates and return vel at the end, called as vx = bounce(x, vx, R, WIDTH - R). It must return because the caller needs the new velocity to store back. A printing version would show the number and change nothing.

Build: a bouncing cabinet

  1. Start from the knob block and build the frame loop underneath it.
  2. One circle, moving, bouncing off all four walls.
  3. Add a probe that prints the position for the first ten frames only.
  4. Change SPEED_X to a number larger than the ball's diameter and run it. Write down what goes wrong.

If time runs out

If pygame is not installed on a machine, chunks 1, 4 and 5 can be run as pure arithmetic with the drawing lines commented out, printing positions only. The numbers are the lesson; the pixels are the reward.

Running this in VS Code

Once, before the first run

Open the terminal in VS Code and install the library: pip install pygame. Check it worked with python -c "import pygame". It should print two lines of greeting from pygame and nothing else. A traceback here is an install problem, not a problem with your program. Those same two greeting lines appear at the top of the terminal every time you run a pygame program; the output boxes on this site leave them out.

Every run after that

The window often opens behind VS Code, so check the taskbar before deciding nothing happened. Close it with its own close button: these programs are written to end when the window closes, and stopping the terminal instead can leave the window stuck on screen. A window that will not close usually means the loop has no pygame.event.get() in it.

There is no turtle anywhere in this course. Turtle needs a library our VS Code setup does not have, so pygame does all the drawing, starting in session 5.
